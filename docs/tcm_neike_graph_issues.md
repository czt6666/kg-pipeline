# 中医内科学知识图谱问题清单

调查方法：search 接口检索、`肝`/`茯苓`节点查邻居、随机抽 10 篇文档核对原文与抽取结果。
以下是已知 4 个问题（同名不同类型/节点对齐/边无强弱/搜索无度数权重）之外的新发现。

---

## 1. 整章内容被错误挂到上一个疾病名下

**描述**：分段脚本没识别出新疾病的章节标题，就把下一整章内容当成上一个疾病的延续，一直
错到再下一个被正确识别的边界为止。gelun 1071 篇文档里，至少 199 篇（约 1/5）疾病标签错误；
咳嗽、哮病、胸痹、胃痛、黄疸、淋证、痉证、痿证、血证、嘈杂、痞满这 11 个常见疾病因此在图
里完全没有自己的节点。

**证据**：
- `data/work/TCM/neike/docs.jsonl` 第 875 行，`doc_id=tcm_neike_gelun_0795`，
  `title="郁证·辨证论治·证治分类·3.咳血"`，正文讲的是咳血的辨证论治，跟郁证无关。
- 同文件里 `title` 以`"郁证·"`开头的文档有两组完整的"病因病机→诊断→辨证论治→
  证治分类→...→古籍摘要"循环（第一组 doc 0764-0785 是真的郁证；第二组 doc 0786-0806
  证治分类是"1.鼻衄 2.齿衄 3.咳血 4.吐血 5.便血 6.尿血 7.紫斑"，是血证）。
- `data/work/TCM/neike/extraction_valid.jsonl` 第 857 行（doc 0787，`title="郁证·病因病机·
  病因"`）：三元组 `{"head":"e1","relation":"病因","tail":"e2"}`，e1=郁证，e2=外邪，而正文
  第一句是"外邪侵袭以风、热、燥、火之邪为主……则引起衄血、咳血、吐血"——这是血证的病因，
  被当成郁证的病因存进了图里。

**解释**：这是 `src/build_tcm.py` 疾病章节边界识别的 bug，不是 schema/prompt 问题。需要
重新核对这几本书的章节边界后重新分段、重抽这部分内容。

## 2. 明确抽出的"别名"关系没有用来合并节点

**描述**：模型能正确识别同义词并抽成"别名"边，但合并节点时完全不看这些边，导致明知道
是同一概念的词还是分成好几个节点。

**证据**：
- `data/work/TCM/merged_neike/edges.jsonl` 第 186 行：`m#100 --别名--> m#579`（"咳血"→"嗽血"，
  来自 doc tcm_neike_gelun_0114）。
- `src/stage7_merge.py` 第 106-107 行：节点合并时的 union-find 只按 `normalize_name(name)+type`
  配对，从未读取 `relation=="别名"` 的边。
- 全量检查 `data/work/TCM/merged_neike/nodes.jsonl`（11531 个节点）：`aliases` 字段全部为空
  数组，没有一个节点用上了这个字段。

**解释**：`aliases` 字段的设计意图就是收集这些别名，但没接上抽取阶段已经产出的信号。
合并逻辑里加一条"用『别名』边做 union-find"就能修，不用改 schema。

## 3. "治法功效"类型没有受控词表，同义表达各自成词

**描述**：`治法功效` 类型 2086 个节点，是全图第二多的类型，其中大量是同一个意思的不同
措辞，模型逐字摘抄原文用词，没做归一化。

**证据**：
- 通过 `/api/merged/TCM/merged_neike/node/m#0`（茯苓）查节点，再在
  `data/work/TCM/merged_neike/edges.jsonl` 里筛 `head=="m#0" and relation=="功效"`
  （第 1、2、3、4、5 行等，共 69 条），尾节点里有：
  `健脾利水 / 健脾利水化湿 / 健脾化湿 / 健脾渗湿 / 健脾除湿 / 健脾胜湿 / 淡渗利水 /
  淡渗分利 / 渗湿利水 / 化湿利水 / 利水渗湿`——同一味药同一个功效被拆成十几个孤立节点。

**解释**：这是问题 2（节点对齐）的一个影响面很大的子类：搜"健脾利水"搜不到"健脾除湿"，
药理上是一回事但图上完全割裂。建议对这类同义词密集的类型做一次归一化/聚类，或在搜索层
做同义词扩展，光靠精确字符串对齐解决不了。

## 4. "用药"/"方用"关系因 domain 限制被系统性丢弃

**描述**：schema 里"用药"关系要求头实体必须是"证候"，不能直接是"疾病"；但原文经常写
"某病直接用某药/某方"，不经过"证候"这一层，这些三元组全部被丢弃。

**证据**：
- `data/work/TCM/neike/warnings.jsonl` 共 661 条 warning，661 条里 571 条是
  `type_violation`，其中 262 条是 `(用药, 疾病, 中药)`、125 条是 `(方用, 疾病, 方剂)`，
  合计 387 条，占全部 type_violation 的 68%。
- 第 101 行具体例子：`doc_id=tcm_neike_gelun_0102`（`title="肺痨·临证备要"`，标签正确，
  排除了问题 1 干扰），`data/work/TCM/neike/docs.jsonl` 第 182 行原文"在辨证基础上加用
  抗结核杀虫药物……如百部、白及、黄连……"，模型正确抽出 `肺痨(疾病) --用药--> 百部`，
  但因为头实体类型是"疾病"不是"证候"，在 `stage2_validate` 校验时被丢弃。

**解释**：CLAUDE.md 里写了"某关系被系统性丢弃较多时，先找用户确认要放宽约束"——这条正好
命中，建议把 `用药`/`方用` 的 domain 放宽到"疾病 | 证候"。

## 5. 边缺权重，`source_doc_ids` 存了但没用上（已知问题 3 的具体证据）

**描述**：图里每条边的来源篇数其实已经记录在 `source_doc_ids` 里，但前端和检索都没拿它
做排序/粗细，边看起来强弱一致。

**证据**：
- 通过 `/api/merged/TCM/merged_neike/node/m#6`（肝）查节点，`data/work/TCM/merged_neike/
  edges.jsonl` 里筛 `tail=="m#6" and relation=="病位"` 共 53 条（如第 316、766、984 行），
  `source_doc_ids` 长度从 1 到 4 不等（第 984 行有 4 篇来源，第 316 行只有 2 篇）——本身
  就带着强弱信号。
- `web/src/pages/GraphExplorer.jsx` 第 227 行：只把 `source_doc_ids.length` 显示成文字
  "出现于 N 篇文档"，没有用来给边设置线宽/颜色深浅。
- `src/retrieval.py`、`src/serve.py` 搜索排序逻辑里没有引用 `source_doc_ids` 长度。

**解释**：不用新增字段，把已有的 `source_doc_ids` 长度接到边的线宽/排序上就是最省事的
权重近似。
